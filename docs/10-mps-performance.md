# M5 无风扇机器的性能排查

本页保留首轮排查证据（累计 56.09 秒）。后续低侵入优化继续使用同一账本，见 [PyTorch MPS 优化实验](11-mps-low-intrusion-optimization.md)，不要以本页旧快照重置预算。

## 基线与方法

复用 `runs/20261117_165850_tonight_awake_folk_f9176f` 的成功记录和中间产物。用户已反馈本次成品与历史 NVIDIA 成品听感基本对齐。本轮不重新生成基线，不使用缓存命中冒充推理加速。

| 阶段 | NVIDIA 历史秒数 | M5 成功阶段秒数 | M5 占比 |
| --- | ---: | ---: | ---: |
| SheetSage2 / MERT | 26.83 | 39.72 | 1.36% |
| YuE2 | 82.69 | 1978.73 | 67.64% |
| BS-RoFormer | 18.25 | 215.38 | 7.36% |
| Seed-VC | 27.82 | 687.26 | 23.49% |
| 准备与混音 | 11.54 | 4.29 | 0.15% |
| 合计 | 167.13 | 2925.37 | 100% |

原环境为 H200，历史调度默认只暴露 GPU 0；不是八卡并行成绩。M5 为 10 核 GPU、24 GB 统一内存。没有重跑 H200，因此不能精确拆分硬件和软件各占多少差距。

局部实验由 `scripts/diagnostics/profile_mps.py` 执行：单 worker 60 秒截止，整个 worker 生命周期计入 300 秒预算，组间强制至少 300 秒冷却。加载、预热和计时分别记录；计时边界同步 MPS。单次 A/B 仅用于定位，不代表稳定统计。`pmset -g therm` 未提供温度数值，“无告警记录”不能证明温度相同。

## 已定位的主要成本

**YuE2 的主问题是 NAR 长序列 attention，以及 AR 随上下文增长的前向成本。** 旧整曲中语义生成 708.15 秒（5122 tokens），NAR 1244.08 秒，VAE 18.40 秒，模型加载/校验只占几秒。

NAR 实际有 28 层、32 步 midpoint，即 64 次网络计算。当前歌曲每层非因果 attention 的 Q 为 `[5123,16,128]`，K/V 为 `[13004,8,128]`。真实尺寸、合成激活的单层探针约 0.55 秒；乘以 28×64 约 990 秒，仅是量级估算，不能直接视为完整 NAR 的算子计时。

固定版本 [PyTorch 2.10 MPS attention 源码](https://github.com/pytorch/pytorch/blob/v2.10.0/aten/src/ATen/native/mps/operations/Attention.mm) 对这里的长 query 使用通用 MPSGraph 路径；短 query 才进入已启用的 vector 快速路径。因此增大上层 query 分块并不会自动得到 CUDA fused attention 的执行效率。本轮 256/512/1024 分块分别约 0.553/0.554/0.559 秒，没有提速，且存在数值差异，未采用分块改动。

额外数值检查使用相同 BF16 输入的 CPU FP32 attention 作为参考，抽查 8 个 query 位置。前 7 个位置最大绝对误差约 0.00012，最后位置（最后一个 3-query 尾块）误差约 0.297；强制连续布局没有改善，512 分块该位置误差约 0.326。该尺寸会进入另一条短 query 快速路径，是后续核查候选；没有进一步做完整路径隔离，不能断言已定位上游根因，也不能据合成输入断言真实歌曲受到何种影响。此数值问题保留为独立待查项，不擅自修改已获试听认可的生成路径。

AR 使用真实权重和既有 token 回放：2759-token 上下文的 8 次前向约 0.767 秒，7864-token 上下文约 1.342 秒。设备审计开启后分别为 0.767/1.358 秒，输出一致。审计不是这次几十分钟耗时的主要解释。CPU 小算子微测约增加 1.71 微秒/调用，也不支持将审计视为首要瓶颈。内存采样未单独做开关 A/B，不宣称其开销已被精确测定。

GPU 采样分布处理的两次调用约 18–38 毫秒；CPU 处理约 2–3 毫秒，但长上下文样本的 scores 并非逐值一致，且没有反复预热验证。本轮不迁移分布计算位置，也不据此宣称确定的提速比例。

**Seed-VC 的扩散网络与 BigVGAN 都有显著成本。** CFM 参数约 1.86 亿，加长度调节器约 1.96 亿，此外还有辅助模型。20 秒真实人声的诊断中，首个 DiT 前向约 1.42 秒，输入为 `[2,128,2580]`（包含 CFG 分支）；用真实源 mel 做 BigVGAN 解码约 8.91 秒。Whisper 两次合计约 0.20 秒、RMVPE 约 0.76 秒、CAMPPlus 约 0.25 秒、长度调节器约 0.24 秒。DiT 为首次前向，不能直接乘 30×11 当作精准整曲耗时；声码器输入是源 mel，也不是完整扩散结果。

整曲 Seed-VC 有 11 个块、每块 30 步。当前 MPS DiT 用 FP32，CUDA 原路径启用 FP16 autocast；这属于已确认的配置差异，收益大小尚未做精度 A/B。本轮保持原精度和步数，不修改质量约束。

**其余环节已检查。** BS-RoFormer 日志显示 26 段循环约 211 秒，每段约 8 秒；源码每段执行模型后将输出送 CPU 做 overlap-add。现有记录不能再精确拆分网络与拼接成本。转谱仅占 1.36%，VAE 约占总耗时 0.63%，准备/混音已比历史更快，均没有继续启动重型探针的必要。

## 本轮修改与边界

新增有超时、预算和冷却限制的局部诊断入口。唯一正式推理修改是 `patches/yue2-mps-sampling.patch`：CPU 抽样后直接在 CPU 读取 token，确实需要下一次模型前向时再传到 MPS，消除原先 CPU → GPU → CPU 的多余标量读回。保留概率、CPU RNG、精度、采样配置、EOS、回调和 CUDA 行为；补丁仍校验固定上游 commit。

这个修改只针对小部分同步开销，不应期待它解决 48 分钟的主要差距。更大的收益需要另外评估 MPS attention 实现/运行时或精度配置，涉及数值与质量验证，不在本轮默认启用。

在 YuE2 相同 Torch 2.10 环境中，各自预热后，32 次采样桥接由 66.69 ms 降为 59.49 ms，token 和 CPU RNG 状态完全一致；这是局部桥接约 10.8% 的差异，不是 AR 或整曲提速 10.8%。按 5122 次线性外推仅约 1.15 秒，且未扣除流水线重叠，因此只是量级估算，未做优化后整曲实测。

微型真实 MPS 模型的随机采样、greedy、CFG 和 EOS 四项回归均与固定上游输出相同；同四项 CPU 回归也通过。原有 26 项测试、4 项预算/冷却/失败退出测试通过。独立只读审查发现的诊断环境与失败退出码问题已修正；补丁重复应用检查通过。

本轮四组 worker（含导入、加载、CPU 部分和微型回归）分别运行 4.59、26.10、17.97、7.43 秒，保守累计 **56.09 秒**，低于 300 秒预算；实际 GPU 活跃时间未单独测量。组间间隔分别为 357.64、322.60、350.13 秒。**整曲重跑次数为 0**，没有通过分阶段整曲重跑绕过限制；基线 WAV SHA256 校验不变。

诊断输出位于 `runs/probes/mps-performance/`，汇总发布在 `configs/macos/performance.json`。现有整曲结果未覆盖。优化后的整曲耗时未经实测，不把局部收益或历史基线当作新成绩。

新补丁改变源码缓存身份，之后正式 `--resume` 会按现有缓存规则重新计算失效阶段；本轮不要用 `--resume` 查看旧结果，直接打开既有交付文件即可。

## 复现局部诊断

```bash
envs/control/bin/python scripts/diagnostics/profile_mps.py nar --run runs/20261117_165850_tonight_awake_folk_f9176f --output runs/probes/mps-performance
# 后续 ar、seed、layout 使用同一 --output；未满 5 分钟冷却会拒绝启动。
```

`nar` 只测真实序列尺寸的 attention；`ar` 是固定 token 回放；`seed` 在第一个 DiT 前向后主动停止，不生成转换音频；`layout` 检查 attention 数值并执行微型采样回归。诊断使用的分块 prefill、单次扩散前向不改变生产设置。不要通过更换输出目录规避累计预算或冷却限制。
